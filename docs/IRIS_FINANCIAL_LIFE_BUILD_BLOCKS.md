# IRIS Financial Life — Six Priority 1 Build Blocks

This document turns the Financial Life / Results experience into six coherent implementation blocks. The blocks are UX boundaries over one IRIS system; they are not intelligence-depth limits, report-count limits, or separate products.

## Block 1 — Arrival & Orientation

Purpose: immediately establish what IRIS can currently see, what is unknown, and where the user can go next.

Required behavior:
- show current evidence state without manufacturing values;
- distinguish connected evidence from derived interpretation;
- expose the complete journey without forcing the user to understand IRIS internals first;
- provide direct paths to Connect, Reports, Evidence and deeper understanding.

## Block 2 — Evidence Connection & Formation

Purpose: make evidence acquisition understandable and governed.

Required behavior:
- distinguish available, consented, authorized, provider response received, persisted, certified, normalized and intelligence-consumable states;
- current Sandbox boundary is seven executable domains;
- Statements remains deferred until real banking;
- never treat catalog definitions as provider evidence;
- never create synthetic user financial facts.

## Block 3 — Observed Financial Life

Purpose: vividly expose the financial reality actually observed by IRIS.

Required behavior:
- accounts and account relationships;
- transactions and temporal activity;
- balances and liquidity where observed;
- identity, assets, liabilities and investments when actually available;
- domain-specific exploration;
- unknown remains unknown rather than becoming zero.

## Block 4 — Change → Understand → Verify

Purpose: turn raw observations into explainable user understanding.

Required behavior:
- change and behavior views;
- relationships and bounded explanations;
- evidence and provenance inspection;
- forward traversal from evidence toward results;
- reverse traversal from a result toward exact runtime lineage when it exists;
- clear separation of observation, calculation, inference, prediction and scenario.

## Block 5 — Report Product Universe

Purpose: make the report catalog the major product surface.

Required behavior:
- catalog definitions can exist before user Plaid data;
- definitions, evidence, intelligence results and published reports remain separate states;
- catalog size is queried from the governed source rather than hardcoded;
- the current persisted count is not an intelligence or report-capacity ceiling;
- browse, search, filter, inspect, activate and deactivate products;
- show runtime/certification state honestly;
- support future dynamic report products whose definitions can emerge from valid intelligence compositions.

## Block 6 — Scenario → Decision → Action → Outcome → Return

Purpose: close the user journey rather than ending at a report.

Required behavior:
- explicit hypothetical scenarios remain separate from observed reality;
- decisions expose evidence and tradeoffs without implying approval;
- Phase 1 remains read-only and does not move money;
- actions may be represented as recommendations or user-controlled next steps without claiming execution;
- outcomes are observations of what actually happened;
- learning feeds the next Financial Life cycle when governed outcome evidence exists.

## Product invariant

All six blocks are connected:

`Arrival → Evidence → Reality → Change/Understanding → Reports → Scenario/Decision/Outcome → Return`

A user can move forward for deeper understanding and backward from a result toward reasoning and evidence. The underlying intelligence hierarchy remains unbounded and is never constrained by the number of navigation routes or catalog definitions.

## Certification boundary

A block is not considered complete merely because a component exists. Completion requires the applicable chain:

`Architecture Defined → Contract Defined → Schema Implemented → Runtime Implemented → Independently Executable → Evidence Verified → Exact Evidence Boundary Verified → Semantic Lineage Verified → Report Product Defined → Report Product User-Controlled → Report Product Surfaced → Interaction Verified → Deployment Verified → End-to-End Certified`
