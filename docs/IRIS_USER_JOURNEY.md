# IRIS Full Consumer User Journey

## Objective

The IRIS journey is one continuous intelligence relationship. It must not feel like a sequence of banking pages. Every stage should reduce uncertainty, increase understanding, or help the user make a better decision while remaining bounded by real evidence.

## Journey

### 1. Arrival

The user immediately understands:

- what IRIS is;
- what it can do;
- what it knows versus does not yet know;
- why connecting evidence matters;
- that IRIS does not fabricate missing financial facts.

The first experience establishes trust before asking for more access.

### 2. Establish the financial-life connection

The user connects an authorized evidence source through the existing governed provider flow. The experience clearly distinguishes availability, consent, authorization, provider response, persistence, observation, and evidence certification.

No provider catalog state is presented as financial truth.

### 3. Evidence formation

IRIS shows the evidence becoming available without exposing implementation noise as the primary experience. Where appropriate, the user can inspect source, freshness, limitations, and coverage.

The system never implies that an incomplete connection is complete.

### 4. First understanding

Once publishable intelligence exists, IRIS leads with the most material supported understanding rather than a pile of metrics.

The user should be able to move naturally from:

`What matters? → Why? → Show me → What changed?`

### 5. Ask IRIS

The user can ask natural questions about their financial life. Each question is evaluated against available evidence and governed intelligence capabilities.

Possible outcomes are explicit:

- answered from supported evidence;
- partially answered;
- insufficient evidence;
- unavailable capability;
- hypothetical/scenario response;
- clarification required.

A question never forces a fabricated answer.

### 6. Explore relationships

The user can move from a result into connected intelligence: transactions, balances, behavior, temporal changes, relationships, risk, opportunity, scenario, or decision analysis where those are actually supported.

The experience exposes relationships rather than requiring the user to know internal capability names.

### 7. Understand the reasoning

Progressive disclosure lets the user inspect:

`Conclusion → supporting intelligence → transformation → upstream intelligence → evidence → source observation`

Where the exact runtime lineage is unavailable, the UI says so instead of implying traceability.

### 8. Compare change

IRIS identifies meaningful changes only when the required temporal evidence exists. It distinguishes observation from calculation, inference, prediction, and scenario.

### 9. Explore what could happen

Scenarios and counterfactuals are explicitly labeled hypothetical. Predictions are not presented as observations. Causal explanations are not presented as proven causation unless the governing runtime certifies that boundary.

### 10. Decide

When supported, IRIS converts intelligence into evidence-linked decision support. The user can understand:

- the decision;
- relevant evidence;
- expected or modeled consequences;
- uncertainty;
- alternatives;
- what would change the recommendation.

IRIS does not silently execute money movement in the current read-only scope.

### 11. Observe outcomes

If a real outcome becomes observable, it is separated from the original prediction or scenario. Outcome evidence can then become input to learning.

No outcome is invented because a recommendation was displayed.

### 12. Learn and return

Real outcomes and new evidence can create new intelligence and higher-order compositions. The next session should feel like continuation of one financial intelligence relationship, not a reset dashboard.

## Journey-wide states

Every major surface must preserve these distinctions:

`Available → Consented → Authorized → Provider response received → Observation persisted → Evidence certified → Intelligence consumable → Intelligence consumed → Report publishable`

No later state may be implied by an earlier state.

## Trust moments

The journey should repeatedly answer four questions without forcing the user to hunt:

1. **What does IRIS know?**
2. **Why does IRIS believe it?**
3. **What does IRIS not know?**
4. **What can I do next?**

## Failure journey

Failures are part of the product journey. If evidence is missing, a provider sync fails, a run is uncertified, lineage is unresolved, or a report is suppressed, the experience should explain the state, preserve user agency, and provide the next valid path without manufacturing completion.

## Journey certification

The journey is not certified by having screens. Certification requires the actual sequence to work against real provider evidence, exact execution boundaries, persisted intelligence, report publication controls, frontend/backend contracts, deployed services, and observable user interactions.
